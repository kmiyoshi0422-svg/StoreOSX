# 現調・完了報告書PDFの速度改善と検証（2026-10-07）

## 変更点

- 従来はA4全ページをプレビューで画像化した後、ダウンロード時に写真を再取得し、DOMをもう一度全ページ画像化していた。
- 現調報告書と完了報告書のプレビューを既存PDF画質プロファイルで一度だけ作成し、**確認した全ページのJPEGをそのままPDFに埋め込む**。PDF履歴への登録・ダウンロードの既存手順は維持。
- 本文、写真、写真ペア、署名が変われば確認済み画像を無効化し、再度プレビューするまでPDF保存不可。プレビュー中に写真が読み込めない場合は画像を置換・捏造せず生成を停止する。PDF内の写真・Before/After・二つの署名・フッターの元レイアウトは変更しない。

## 同条件の合成ブラウザ計測

Chromium上で写真2枚・署名欄・長文を含むA4縦6ページを作成し、同一ページのJPEG画質・html2canvas倍率を揃えて一回計測した。比較は**ダウンロードボタンを押してからPDF組み立てまでのクライアント処理**であり、ネットワーク上の実写真やPDF履歴アップロード、利用端末差は含まない。

| 項目 | 旧方式 | 新方式 |
| --- | ---: | ---: |
| A4プレビューのページ描画 | 別途必要 | 884ms（PDF画質で一度） |
| ダウンロード時の再描画＋PDF組み立て | 749ms | 17ms（再描画なし） |
| 生成PDF | 6ページ、680,473バイト | 6ページ、680,371バイト |

**注記:** この749ms→17msは合成条件での一例であり、実案件の所要時間や削減率を保証しない。プレビュー開始時の処理は高画質化と写真の先読み分、従来より長くなり得る。大量写真・低メモリ端末では既存プロファイルで縮小する。

- `reportLayout.contract.test.ts`：A4プレビュー必須、Before/After比較、二者署名を維持し、確認済み画像をそのまま両報告書のPDFへ使用。
- Chromiumの合成6ページPDFを`pdfinfo`でA4・全6ページと確認し、先頭・最終ページの写真、文字、署名欄が見切れないことを目視確認。破損画像を使ったブラウザ検証ではプレビューを止め、元画像URLを復元することを確認。
- 認証済み開発プレビューで実案件の現調／完了報告書の編集画面表示を確認。**実案件の写真付きA4モーダルを開いてダウンロードするE2E計測は今回実施していない。**
