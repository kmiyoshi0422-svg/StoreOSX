# 案件責任者5名の入替管理

## 操作場所

最高管理者でログインし、メニューの **案件責任者の入替**（`/settings/responsibility`）を開きます。他の管理者・役員・社員・協力業者・顧客にはこの管理メニューを出さず、管理APIでも拒否します。

## 入替手順

1. 「新しい責任者」5欄で、在籍中の社内ユーザーを選択します。現在の5名はすべて変更できます。初回ログイン前の事前登録だけの人・退職者・協力業者・顧客は選択対象になりません。追加したい人がいなければ、先に「社員追加・退職管理」で登録し、本人の初回ログイン後に選択してください。
2. 同じ人を複数欄には選べません。5名同士の位置を変える場合は一度「未選択」に戻します。位置には権限の優劣はありません。
3. 変更理由を入力し、「内容を確認」で変更前後の5名を確認します。確認画面を開いただけでは保存しません。
4. 「5名の入替を確定する」で保存します。保存中は編集・再送信を停止します。別画面で名簿が更新されていた場合は上書きせず、入力を残して最新状態を再取得します。

## 連動する機能

案件新規登録、案件一覧・詳細の責任者選択、未決定アラートからの個別・一括割当は、現在の責任者名簿を使います。一度開いた画面の名簿も定期的に再取得し、APIは保存直前に現行メンバーの資格を再検証します。退職・社外区分のメンバーへ新規割当はできません。

未決定アラートの基準（依頼日2026年10月1日以降、登録後120時間以上、未決定・未完了）は変更しません。入替で外れた人への新しい未決定アラートは停止し、新しい本人アカウントを対象とします。

## 自動で変更しない情報

責任者名簿の入替は、ログイン可否、利用者区分、金額・利益閲覧権限、閲覧エリア、作業担当者、協力会社、既存案件の責任者、ステータス、対応日を変更しません。最高管理者自身を責任者5名から外しても、最高管理者の管理権限は失いません。

旧責任者の人物キーと名前は「過去の責任者」として保持し、既存案件・変更履歴を別人の名前に付け替えません。案件一覧の責任者検索では旧責任者も検索でき、旧本人の社内アカウントには既存の責任・作業担当案件の個別集計が残ります。ただし旧責任者を新規割当対象に戻すには、この管理画面で現在の5名へ再登録する必要があります。退職した本人のアクセスは既存の利用停止ガードで拒否します。

必要な引継ぎは、対象案件の責任者を別途変更してください。名簿の保存と案件の引継ぎを分離しています。

## 保存・監査

現在の5名・旧メンバー・設定バージョンを専用設定 `responsibility.roster.v1` で保存し、`responsibility_roster_logs` に変更前後、理由、操作者、日時を同じトランザクションで記録します。既存の本人確認設定や利用者の権限は上書きしません。初期状態は従来の5名と確認済みアカウントから生成し、実際に管理画面で入替を確定するまで現行構成を変更しません。

DBマイグレーション0057では `cases.responsible_officer` を既存の文字列を保持できるVARCHAR(32)に拡張し、独立した監査テーブルだけを追加しました。既存案件への責任者一括移管は行っていません。

## 検証方法

責任者入替APIの保存・競合・旧人物保持・本人アラート・一括割当・外部拒否は、実DBの未コミットトランザクション内で合成データを使い、最後にすべてロールバックする回帰テストで検証します。実会社の5名をテストで入れ替えません。

PC・スマホの選択・確認・取消・保存中・履歴表示・新規登録選択欄への連動は、管理名簿と保存応答を合成データにした実ブラウザで検証します。実ログインによる非owner画面・メニューの拒否も確認します。公開サイトの認証済み実メンバー入替操作は、今回ユーザーが新しい5名を指定していないため行いません。

### 公開前の権限レビューで追加した保護

汎用アプリ設定APIとDB保存ヘルパーから、責任者名簿・確認済み本人設定の書込みを拒否します。一般設定一覧にも本人メール設定や生の名簿設定を返しません。最高管理者も、名簿の変更には専用の監査付き管理APIを使います。

名簿保存後に同じ本人が別のログインIDで現れた場合も、確認済み本人対応・同じ本人メールから現在／過去の同じ人物キーへ解決します。同じ本人を別IDの2人として責任者に登録する操作を拒否し、旧案件の名前と集計を維持します。

アラート一括割当では、名簿行のロックを取得した後に実行者本人の現メンバー資格をもう一度確認します。入替と競合して直前に5名から外れた場合も、旧画面からの一括割当を停止します。これらは専用の回帰テストで検証しています。

名簿の実DBロールバックテストは、共有設定行を未コミットでロックするため他ファイルと同時実行しません。全体収支の増減を測る既存テストも他の合成案件作成／削除の途中状態を拾わないよう、Vitestの実行グループを分離しました。これにより通常のテストコマンドでも同じ検証順序を再現できます。実会社の設定を検証用の5名に変更してから戻す方式は使っていません。
